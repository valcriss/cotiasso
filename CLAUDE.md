# CLAUDE.md

Application web de gestion associative et de comptabilité en partie double, en marque blanche, licence MIT. Une installation = une association (pas de multi-tenant).

**État du projet : lot 0 (conception) en brouillons dans `docs/lot0/`, non validés par le trésorier du pilote ; implémentation du lot 1 démarrée sur décision de l'utilisateur (31 octobre 2026). Les livrables du lot 0 restent la référence fonctionnelle mais peuvent évoluer à la validation. Un audit du point de vue d'un trésorier débutant (2 novembre 2026) a conduit aux parcours simplifiés de l'[ADR 0028](docs/decisions/0028-parcours-simplifies-pour-tresoriers-novices.md), qui remplacent certaines directives antérieures (menu, plan de comptes, premier compte, vue d'ensemble).**

## Public cible et pédagogie (priorité sur le reste de l'interface)

**L'application s'adresse à des trésorier·ères d'association bénévoles qui n'y connaissent rien en comptabilité.** La rigueur comptable est l'affaire du logiciel ; **tout doit être fait pour leur faciliter la tâche et leur permettre de comprendre** ce qu'ils font et pourquoi. Concrètement, pour tout écran, message ou fonction :

- **Parler simple** : mot courant d'abord (« argent qui entre / qui sort »), terme comptable gardé mais **toujours expliqué** à côté (il servira face à un expert-comptable).
- **Expliquer à quoi ça sert** : phrase de description sous le titre de chaque page, aide et exemple sur les champs non évidents, **état vide qui dit quoi faire en premier**.
- **Guider** : valeurs par défaut sûres, contrôles au fil de l'eau, actions impossibles masquées ou expliquées.
- **Messages d'erreur à trois temps** : ce qui s'est passé, pourquoi, que faire maintenant. Jamais de code technique ni de ton accusateur.
- **Montrer les conséquences avant les actions irréversibles** (comptabiliser, clôturer…) et **rassurer** (brouillon, contrepassation : une erreur se corrige).
- **Cohérence** : même geste, même mot, même emplacement partout.
- **Deux affichages** ([ADR 0028](docs/decisions/0028-parcours-simplifies-pour-tresoriers-novices.md)) : l'affichage **Simple** est le défaut et celui qu'il faut concevoir en premier (« J'ai reçu / J'ai dépensé de l'argent », catégories en mots courants, aucun numéro de compte ni débit/crédit imposé) ; l'affichage **Comptable** garde tout le vocabulaire pour l'expert. Un écran destiné au quotidien du trésorier ne doit **jamais** exiger de connaître la partie double : il la montre en lecture (« Ce que verra l'expert-comptable »), il ne la demande pas.

Une fonction n'est pas terminée tant qu'une personne sans connaissance comptable ne peut pas l'utiliser sans explication orale. Le détail (structure des pages, barre d'action, boîtes de dialogue, descriptions, retours à l'utilisateur) est dans **[design.md](design.md)**, à suivre pour toute nouvelle page.

## Commandes

Node épinglé dans `mise.toml` (26.12.1) ; gestionnaire de paquets : npm (workspaces). Préfixer par `mise exec --` si les shims ne sont pas actifs. Toutes les commandes se lancent à la racine :

- `npm install` : installe le monorepo.
- `npm run dev` : lance en parallèle (via `concurrently`, après avoir compilé le domaine) le watch du domaine, l'API et le front ; `npm run dev:api` (qui compile d'abord le domaine, sans le surveiller) et `npm run dev:frontend` lancent chacun seul. (`npm run … --workspaces` exécute les workspaces l'un après l'autre : le watch de l'API bloquerait le front.)
- `npm run build` : compile tous les workspaces. **L'API importe `@cotiasso/accounting-domain` depuis son `dist`** : `dev`, `build`, `typecheck`, `test` et `test:integration` compilent donc d'abord le domaine (`npm run … --workspaces` suit l'ordre alphabétique, `apps/` avant `packages/`).
- `npm test` : lance les tests de tous les workspaces ; `npm run test:watch` en continu.
- `npm run typecheck` : vérification des types.
- `npm run clean` : supprime les sorties de build.
- `cp .env.example .env` (première fois), puis `npm run db:up` : démarre PostgreSQL en Docker via `docker-compose.dev.yml` (projet `cotiasso-dev`, port 5433) ; `npm run db:down` l'arrête (le volume de données est conservé). Après un `db:up` sur base vierge, appliquer les migrations avec `npm run db:migrate`.
- `npm run db:generate` (client Prisma, requis après `npm install` et tout changement de schéma) ; `npm run db:migrate` crée/applique une migration.
- `npm run test:integration` : tests sur la vraie base (nécessite `db:up` et les migrations appliquées). `npm test` n'a pas besoin de base.

CI : `.github/workflows/ci.yml` (GitHub Actions, Node 26.12.1, PostgreSQL 17 en service) rejoue sur chaque push vers `main` et chaque pull request : `npm ci`, `db:generate`, typecheck, tests, build, migrations, tests d'intégration. Toute nouvelle vérification locale doit être ajoutée à ce workflow.

Production : `Dockerfile` multi-étapes avec deux cibles, `api` (Node 26.12.1, utilisateur non root, applique `prisma migrate deploy` au démarrage puis lance `dist/main.js`) et `web` (nginx non privilégié sur le port 8080, sert l'Angular compilé et proxifie `/api/` vers `api:3000`). `docker-compose.yml` est l'exemple de déploiement : `cp .env.prod.example .env.prod`, renseigner `POSTGRES_PASSWORD` et `COTIASSO_VERSION`, puis `docker compose --env-file .env.prod up -d --build`. La base n'est jamais publiée ; le HTTPS est à la charge du reverse proxy placé devant `COTIASSO_HTTP_PORT`. `prisma` est une dépendance (pas une devDependency) de l'API car l'image l'exécute au démarrage. Le Compose de développement (`docker-compose.dev.yml`) reste distinct.

Workspaces :
- `packages/accounting-domain` : TypeScript pur, Vitest.
- `apps/api` : NestJS 12 + Fastify (ESM), Prisma 7 (adaptateur `pg`). `GET /health` vérifie la base. L'API écoute sur `API_HOST:API_PORT` (3000 par défaut).
- `apps/web` : Angular 22 + Angular Material 22 (thème Material 3 azure/bleu dans `src/styles.scss`, variables `--app-sidebar-*` pour la marque blanche), tests Vitest via `ng test`. `npm run dev -w @cotiasso/web` sert sur http://localhost:4200 (utiliser `localhost`, pas `127.0.0.1`) et proxifie `/api/*` vers l'API en retirant le préfixe `/api`. Polices et icônes sont hébergées localement (`@fontsource/roboto`, `material-icons`), jamais chargées depuis un CDN. Authentification côté web (`src/app/auth/`) : `AuthService` (signaux `user` et `setupRequired`, jeton CSRF gardé en mémoire uniquement, jamais en stockage navigateur), intercepteur `csrfInterceptor` (ajoute `x-csrf-token` aux requêtes modifiantes et renvoie vers `/connexion` sur un 401 de route protégée), gardes `authGuard`/`loginGuard`/`setupGuard`. Routes : `/connexion`, `/installation` (tant qu'aucun compte n'existe), et la zone authentifiée dans `Shell`. L'état initial se décide une fois (`initialize()`) ; un rechargement de page retrouve la session grâce au cookie. Administration web (`src/app/admin/`) : `/parametres` (permission `settings.association:view`) est une page à onglets dont les rubriques `Utilisateurs` et `Rôles` exigent `users:view` ; les actions de modification n'apparaissent qu'avec `users:admin`, mais le serveur reste l'autorité. `Utilisateurs` : invitation (lien affiché une seule fois, jamais stocké côté web), liens de réinitialisation, rôles, désactivation avec confirmation, déconnexion partout. `Rôles` : liste, création, édition des permissions groupées par ressource. `/compte` (tout utilisateur connecté, via son nom dans le menu) : changement de mot de passe. Les tests de pages utilisent `src/app/testing/auth-mock.ts` pour fixer les permissions. TypeScript est aligné sur 6.0.3 dans tout le dépôt : Angular 22 exige `>=6.0 <6.1` (compiler-cli et build), ce qui bloque TypeScript 7 tant qu'Angular ne le supporte pas. Migrer l'ensemble vers 7 en une fois quand ce sera possible, sans désaligner les workspaces.

Conventions de l'API :
- Injection explicite avec `@Inject(TOKEN)` partout : le code est exécuté par tsx/esbuild, qui n'émet pas `emitDecoratorMetadata`.
- Imports relatifs avec extension `.js` (ESM NodeNext).
- Authentification (`apps/api/src/auth/`, conception dans l'[ADR 0007](docs/decisions/0007-authentification-conception.md)) : hachage argon2id avec `node:crypto` (pas de dépendance native), politique de mot de passe locale, `UsersService` (création, vérification des identifiants à temps égal, changement de mot de passe). Les comptes ne se suppriment jamais (déclencheur SQL) : on les désactive. Les tests d'intégration créent des emails uniques en `@test.invalid` sans nettoyage.
- Sessions (tâche 2 du lot 1.2) : `AuthGuard` est global avec refus par défaut ; seules les routes marquées `@Public()` (login, health) s'ouvrent sans session. Cookie `__Host-cotiasso_session` (`httpOnly`, `Secure`, `SameSite=Lax`) ; sans HTTPS en développement, `COOKIE_SECURE=false` (déjà dans `.env.example`) et le nom perd son préfixe. Toute requête non GET/HEAD/OPTIONS exige l'en-tête `x-csrf-token` (valeur renvoyée par `/auth/login` et `/auth/me`). Endpoints : `POST /auth/login`, `GET /auth/me`, `POST /auth/logout`. Durées : `SESSION_IDLE_MINUTES` (120) et `SESSION_MAX_HOURS` (12).
- Anti-brute-force : 5 échecs tolérés par compte et 20 par IP sur 15 min, puis délai doublé à chaque échec (plafonné à 15 min), renvoyé en `429` + `Retry-After`. Jamais de verrouillage définitif. En production, `TRUST_PROXY=true` côté API et nginx remplace `X-Forwarded-For` par l'IP réelle ; `TRUSTED_PROXY_CIDR` (dans `.env.prod`) désigne le reverse proxy HTTPS autorisé à fournir l'IP du client. Sans cela, un client ne peut pas falsifier son IP.
- Assistant initial (tâche 3, `apps/api/src/setup/`) : tant qu'aucun compte n'existe, l'API génère au démarrage un jeton à usage unique affiché **uniquement dans les logs** (`docker compose logs api`) ; seule son empreinte est stockée et chaque démarrage remplace les jetons inutilisés. `GET /setup/status` (public) indique si l'installation est requise ; `POST /setup` {token, email, displayName, password} crée le premier compte et ouvre sa session. Atomique (jeton verrouillé `FOR UPDATE`) : une seule création même en concurrence, et un mot de passe refusé ne consomme pas le jeton. Le compte créé reçoit le rôle « Administrateur technique » dans la même transaction, et **aussi** « Trésorier » si `alsoTreasurer` est vrai (case cochée par défaut, ADR 0028) : l'administrateur technique seul n'a aucun droit métier. Les tests qui exigent une base sans utilisateur créent une base jetable via `test/integration/support/temp-database.ts`.
- Autorisation (lot 1.3, `apps/api/src/authz/`, [ADR 0008](docs/decisions/0008-autorisation-roles-et-permissions.md)) : **toute nouvelle route doit déclarer son accès** avec `@Public()`, `@Authenticated()` ou `@RequirePermission('ressource:action')` ; sans déclaration elle est refusée, et un test d'intégration échoue. Les permissions viennent du catalogue `permissions.ts` ; les rôles (modifiables, installés par `default-roles.ts`) sont en base. Ne jamais tester un nom de rôle dans le code. Au moins un compte actif doit garder `users:admin` : toute opération qui peut retirer des droits (révocation, modification de rôle, future désactivation de compte) prend `RolesService.lockLockout` puis appelle `assertAdministratorRemains` dans sa transaction. Les attributions de rôle ne se suppriment pas (déclencheur SQL). **Portée projet** ([ADR 0022](docs/decisions/0022-portee-projet-des-droits.md)) : `RoleAssignment.projectId` (immuable, déclencheur SQL ; absent = global). Seules les permissions de `PROJECT_SCOPABLE_PERMISSIONS` (`projects:view`, `projects:update`, `grants:view`, `documents:view`, `documents:create`) s'exercent sur un projet : une attribution à portée projet n'accorde **que l'intersection** rôle ∩ liste, jamais le reste du rôle. `permissionsFor` (base de `@RequirePermission`) **ne lit que les attributions globales** ; les accès par projet se lisent à part (`projectAccessFor`, `scopedAccess`). Routes sur des projets : `@RequireProjectAccess('projects:view')` (droit global ou sur au moins un projet) → le garde pose `request.projectAccess` et **le service filtre** ; un projet hors portée est **introuvable (404)**. Créer un projet reste un droit global. Les attributions à portée projet **ne comptent pas** pour la règle du dernier administrateur. `/auth/me` renvoie `projectPermissions` ; côté web `AuthService.canOnProject` et `canAny` (menu, gardes de route) ; l'écran « Accès effectifs » est la boîte « Voir les accès » de la page Utilisateurs.
- Gestion des comptes (tâche 4 du lot 1.2, `auth/accounts.controller.ts`) : un administrateur (`users:admin`) crée un compte (`POST /users`, rôles optionnels) qui n'a **aucun mot de passe utilisable** et reçoit un lien d'invitation (72 h) ; `POST /users/:id/password-reset` émet un lien de réinitialisation (24 h) ; `disable`/`enable` (jamais son propre compte, protégé par la règle du dernier administrateur) ; `sessions/revoke` déconnecte partout. Le lien est `/reinitialisation#token=…` : le jeton est dans le **fragment** pour ne jamais atteindre un journal serveur, la page web le retire de la barre d'adresse. `POST /auth/password-reset` (public, ralenti par IP) consomme le jeton une seule fois, atomiquement, et révoque les sessions ; `POST /auth/password` change son propre mot de passe (autres sessions révoquées). Seule l'empreinte du jeton est stockée ; un jeton n'est montré qu'une fois et n'est jamais journalisé. Un administrateur peut émettre un lien pour n'importe quel compte : c'est tracé dans l'audit (`user.password-reset.issued`).
- Authentification à deux facteurs (tâche 5 du lot 1.2, `apps/api/src/mfa/` et `auth/mfa.*`) : TOTP RFC 6238 écrit sans dépendance (vecteurs officiels testés), HMAC-SHA1, 6 chiffres, 30 s, tolérance ±1 pas, **un pas ne sert qu'une fois** (`lastUsedStep`, mise à jour conditionnelle contre le rejeu). Les secrets sont **chiffrés au repos en AES-256-GCM** avec `MFA_ENCRYPTION_KEY` (32 octets en base64, obligatoire, lié à l'utilisateur) : **cette clé doit être sauvegardée avec la base**, sans elle tous les seconds facteurs sont illisibles. 10 codes de secours à usage unique, stockés en HMAC-SHA256 avec cette même clé. `Role.requiresMfa` (vrai par défaut pour l'administrateur technique et le trésorier) : l'exigence est recalculée à **chaque requête**, un rôle devenu exigeant s'applique aussitôt aux sessions en cours. Une session dont le second facteur n'est pas vérifié (`VERIFICATION_REQUIRED`) ou pas encore activé alors qu'un rôle l'exige (`ENROLLMENT_REQUIRED`) est **partielle** : `PermissionsGuard` refuse tout (403 `MFA_REQUIRED`) sauf les routes marquées `@AllowPartialSession()` (`/auth/me`, `/auth/logout`, `/auth/mfa/verify`, `/auth/mfa/enroll/*`), et `/auth/me` ne renvoie aucune permission. Essais de code ralentis par la même limite que la connexion. Un administrateur peut réinitialiser le MFA d'un compte (`POST /users/:id/mfa/reset`, audité, sessions révoquées). Le QR code est généré dans le navigateur (`qrcode`), le secret ne passe par aucun service tiers. **Récupération d'urgence** si le seul administrateur perd son appareil et ses codes : `docker compose exec api node dist/cli/reset-mfa.js <email>` (ADR 0028), sans SQL ; le service applicatif révoque les sessions et consigne `user.mfa.reset` (sans acteur, `via: "serveur"`) dans le journal chaîné. Il se réinscrira à la connexion suivante. Les tests qui n'ont pas pour objet le MFA désactivent `requiresMfa` sur les rôles après l'installation ; `test/integration/mfa.test.ts` conserve les valeurs par défaut.
- Paramètres, marque blanche et modules (lot 1.4, `apps/api/src/settings/`) : les paramètres sont des **versions** (`SettingsVersion`, section + JSON, ajout seul par déclencheur SQL, date d'effet) validées par un schéma **zod** (`schemas.ts`) avant écriture ; la valeur en vigueur est la dernière version dont `effectiveFrom` est passé, complétée par les valeurs par défaut si le schéma a gagné des champs. Une modification sans effet ne crée pas de version ; l'audit ne garde que les clés modifiées, jamais les valeurs. Sections : `identity` (nom, adresse, contacts, RNA, SIREN) et `branding` (nom affiché, couleurs du menu, **contraste WCAG AA ≥ 4,5 imposé côté serveur**). `GET /branding` est public (la page de connexion est déjà aux couleurs de l'association) ; lecture des paramètres : `settings.association:view`, écriture : `settings.association:admin`. Pour ajouter une section : un schéma + des valeurs par défaut dans `SETTINGS_SECTIONS`, rien d'autre. **Modules** (`modules-catalog.ts`, ADR 0002 et 0003) : catalogue injectable (`MODULE_CATALOG`) ; un module `available: false` ne peut pas être activé (409, avec son motif), ni un module dont un prérequis est inactif ; on ne désactive pas un module dont un module actif dépend ; activation réservée à `settings.accounting:admin`. **Aucun module n'est livré pour l'instant** : en passer un à `available: true` exige son implémentation et sa validation sur le jeu de référence. Côté web, `BrandingService` charge la marque blanche avant le premier affichage (`provideAppInitializer`) et pose `--app-sidebar-*` et le titre de la page. Les styles partagés des pages (titres, panneaux, tableaux, onglets, alertes, sections de formulaire) sont dans la feuille **globale** `apps/web/src/app-ui.scss` ; `admin-pages.scss` ne garde que l'hôte des composants (budget de style par composant).
- Journal d'audit (lot 1.5, `apps/api/src/audit/`) : `AuditEvent` est en ajout seul (déclencheurs SQL, y compris `TRUNCATE`) **et chaîné** : chaque événement porte `previousHash` et `hash` = SHA-256 de l'empreinte précédente et du contenu en JSON canonique (clés triées, car `jsonb` ne conserve pas leur ordre). `AuditService.record` écrit sous un verrou consultatif pour garder la chaîne linéaire (ne pas contourner : tout événement passe par lui). `GET /audit` (filtres action, objet, acteur, période ; pagination par curseur `seq`, 200 max), `GET /audit/facets`, `GET /audit/verify` (recalcule toute la chaîne et désigne le premier événement altéré, retiré ou forgé), tous sous `audit:view`. `GET /audit/csv` (mêmes filtres, [ADR 0025](docs/decisions/0025-export-audit-et-fichier-ofx-d-origine.md)) exporte en CSV sûr, du plus ancien au plus récent, **avec les empreintes** de chaque événement (copie de contrôle, pas archivage probant), 20 000 événements au plus (au-delà : 422, jamais de troncature), et se consigne lui-même (`report.exported`, `kind: audit`). Les événements antérieurs à la chaîne (`hash` nul) sont conservés mais déclarés « non vérifiables ». **La chaîne détecte une altération faite en base ; elle n'est pas un archivage probant** (cadrage §11.2) : l'écran le dit. `seq` est un `BigInt` : les tests qui sérialisent des lignes Prisma passent par `test/integration/support/bigint-json.ts`. Libellés français des actions dans `apps/web/src/app/admin/audit-labels.ts` : y ajouter toute nouvelle action d'audit.
- Documents (lot 1.6, `apps/api/src/documents/`) : un **document logique** (`Document`), des **versions immuables** (`DocumentVersion`, déclencheur SQL ; remplacer un fichier crée une version, numérotée sous verrou `FOR UPDATE`), des **liens multiples** vers d'autres objets (`DocumentLink`, sans clé étrangère car les objets arrivent plus tard ; types dans `categories.ts`). **Un document ne se supprime pas, il s'archive** (déclencheur sur `DELETE`) ; retirer un lien ne supprime jamais le document. Fichiers sur disque dans `DOCUMENTS_DIR` (volume `documents-data` en production, **à sauvegarder avec la base**), sous une **clé opaque** `AAAA/MM/uuid` générée par le serveur (le nom d'origine, nettoyé par `sanitizeFilename`, ne sert jamais de chemin ; `DocumentStorage` refuse toute clé hors de ce format). Dépôt multipart en **flux** (jamais en mémoire), taille limitée (`DOCUMENTS_MAX_MB`, 25 par défaut), empreinte SHA-256 calculée à l'écriture. **Liste blanche stricte** (`file-types.ts`) : pdf, png, jpg, docx/xlsx/pptx/odt/ods/odp, csv, txt ; le contenu (signature) **et** l'extension doivent concorder ; HTML, SVG, scripts, exécutables et archives sont refusés (415). Le type servi est celui détecté, jamais celui du client. Téléchargement toujours en pièce jointe avec `nosniff`, `Content-Security-Policy: sandbox` et `no-store`. Un fichier déjà déposé est **signalé sans être bloqué**. Un document `restricted` est invisible (404, y compris en liste et en recherche) sans `documents.restricted:view`, et son téléchargement est audité. Tout fichier déjà écrit doit être retiré si l'opération échoue : le contrôleur et le service le font (opération idempotente), un test le vérifie. `configureApp()` (`app.setup.ts`) enregistre multipart : à appeler dans `main.ts` **et** dans les tests qui déposent des fichiers. **Portée projet (lot 4.5, [ADR 0024](docs/decisions/0024-projets-budgets-et-financements.md))** : `documents:view` et `documents:create` sont applicables à un projet. Lecture, dépôt, version, modification de titre ou catégorie et ajout de lien passent par `@RequireProjectAccess` ; **archivage, désarchivage et retrait de lien restent `@RequirePermission` (droit global)**. Le contrôleur pose `Viewer.scope` (ids des projets) ; **toute lecture passe par `DocumentsService.access()`** (liste, détail, téléchargement, doublons signalés, filtre par objet lié) : une personne limitée à des projets ne voit qu'un document **lié à l'un de ses projets ou à une subvention qui en finance un, et jamais lié à un membre** ; hors portée, **404** (jamais « pas à vous »), et seuls les liens de sa portée sont renvoyés (et comptés). **Dépôt limité** : au moins un lien, et uniquement vers ses projets ou leurs subventions (sinon 403) ; jamais de document restreint ni de changement de ce caractère. Un document restreint garde `documents.restricted:view` (global). La page Documents générale et sa route restent **globales** (`NavigationItem.global`, `data.global` du `permissionGuard`) ; les documents d'un projet ou d'une subvention se lisent depuis leur fiche (`documents/linked-documents.ts`, qui réutilise `UploadDialog` avec `links`). Les tests d'accès sont dans `documents-scope.test.ts` (17 cas) : **tout nouveau chemin de lecture d'un document doit passer par `access()` et y être couvert**.
- Structure comptable (lot 2a.2, `apps/api/src/accounting/`, [ADR 0009](docs/decisions/0009-structure-comptable-exercices-journaux-comptes.md)) : `FiscalYear`, `Journal`, `Account`. **Les garanties sont en SQL** (migration `add_accounting_base`) : exclusion de chevauchement des exercices, statut qui n'avance que vers `CLOSED`, aucune suppression, numéro de compte et code/type de journal définitifs ; le service ajoute des erreurs lisibles (409) et l'audit. **Aucun plan de comptes n'est imposé ni validé** : import « numéro;libellé », saisie, ou le **modèle de démarrage proposé** de l'ADR 0028 (optionnel, à faire relire par un expert-comptable). Lecture `entries:view`, écriture `settings.accounting:admin`. Les dates sont des chaînes `AAAA-MM-JJ`. Onglet web Paramètres › Comptabilité. Les statuts `CLOSING`/`CLOSED` ne sont pas encore atteignables par l'API (clôture en 2a.3).
- Écritures (lot 2a.3, `apps/api/src/accounting/entries.*`, [ADR 0010](docs/decisions/0010-ecritures-comptabilisation-et-contrepassation.md)) : `JournalEntry`/`JournalLine`/`EntryCounter`. **La comptabilisation est un déclencheur SQL** (`journal_entry_guard`) : le service passe seulement `status` à `POSTED`, la base vérifie l'équilibre, ≥ 2 lignes, comptes et journal actifs, date dans l'exercice, exercice `OPEN` **sous verrou partagé** (donc une clôture concurrente attend ou refuse, CA-04), puis attribue le numéro par incrément du compteur. Une écriture comptabilisée et ses lignes sont immuables ; on la **contrepasse** (`POST /entries/:id/reverse` : écriture inverse reliée, comptabilisée dans la même transaction, original → `REVERSED`). `TRUNCATE` est refusé sur toutes les tables comptables (il contournerait les déclencheurs de ligne et ferait réattribuer des numéros). Brouillons : contrôle de version optimiste (`version`), suppression permise. Montants en chaînes, `Money` du domaine pour les totaux. Droits : `entries:view`, `entries:create` (brouillons), `entries:post` (comptabiliser, contrepasser). ## Règles non négociables du domaine

- Comptabilité en partie double : débit = crédit à la validation, atomique, numérotation unique garantie en base, écriture validée non modifiable (contrepassation reliée).
- Montants : PostgreSQL NUMERIC + lib décimale côté TS ; décimaux en chaînes dans l'API ; jamais de `number` flottant pour de l'argent.
- Transaction (mouvement bancaire) ≠ écriture comptable : tables séparées. Rapprochement bancaire, affectation de paiement et lettrage sont trois mécanismes distincts.
- Données brutes d'import conservées sans réécriture ; imports idempotents, pas de doublons silencieux.
- Autorisation : refus par défaut, vérifiée côté backend à chaque opération (listes, recherche, exports, téléchargements inclus). Rôles = modèles modifiables, pas de privilèges codés en dur.
- Fonctions optionnelles (TVA, immobilisations, constatés d'avance, factures non parvenues, fonds dédiés…) = modules activables par association ([ADR 0002](docs/decisions/0002-modules-activables-et-regles-comptables.md)). Exercices et TVA sont paramétrables, jamais codés en dur pour l'association pilote.
- Un mode de TVA ou un module n'est activable qu'une fois implémenté ET validé sur le jeu de référence ; sinon « indisponible » ([ADR 0003](docs/decisions/0003-perimetre-tva-et-modules-ajustement.md)).
- Les décisions Q1 à Q10 du cadrage sont tranchées dans `docs/decisions/` (ADR 0001 à 0006) ; les relire avant toute conception.
- Cotisations : produit constaté à l'encaissement, pas de créance comptable par défaut.
- Configuration déclarative uniquement (pas de scripts). Option non prise en charge = explicitement indisponible, jamais acceptée avec traitement partiel.
- Aucune affirmation de conformité comptable/fiscale (TVA, FEC, reçus fiscaux) sans périmètre vérifié.
- Pas de secrets, données ou documents d'association dans le dépôt.
